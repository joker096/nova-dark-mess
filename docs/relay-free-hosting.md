# Бесплатное размещение резервного relay

Дата: 2026-11-21. Цель — поднять второй relay без покупки второго VDS, чтобы
заработала standby-очередь из `docs/relay-standby.md`.

## Что подходит, а что нет

| Вариант | Бесплатно | Always-on | Подходит для relay |
|---|---|---|---|
| **Northflank Sandbox** | Да, 2 сервиса + 1 БД | Да, без сна | **Да, как временный резерв** |
| **Oracle Cloud Always Free** | Да, VM | Да | Да, лучший бесплатный вариант, но это второй сервер |
| Render Free | Да | Нет, сон через 15 мин | Нет: процесс засыпает, очередь в памяти теряется |
| Koyeb Free | Для новых аккаунтов фактически нет | — | Нет |
| Railway | Только trial/малый кредит | — | Нет для постоянного relay |
| Cloudflare Workers + Durable Objects | Да, без карты | Да | Технически да, но нужен порт relay на Workers; сейчас не реализовано |
| Cloudflare TURN / Metered TURN | Да | — | Нет: это WebRTC, а не очередь сообщений |

Очереди теперь сохраняются в SQLite-файл (`ANON_STATE_DB_PATH`), поэтому
перезапуск процесса их не стирает. Для контейнера нужен **persistent volume**,
смонтированный в `/data`: без него перезапуск контейнера сохранит данные только
в пределах его writable layer, а пересоздание — нет.

Хост всё равно должен быть always-on: спящий процесс не принимает сообщения,
даже если база цела.

## Вариант 1: Northflank Sandbox (быстро, без VDS)

В репозитории уже есть `Dockerfile` для relay-only образа и `.dockerignore`.

1. Зарегистрироваться на Northflank и выбрать план **Sandbox**.
   По документации Northflank для создания ресурсов может потребоваться
   привязка карты только для верификации; уточните условия на момент регистрации.
2. Создать проект и сервис типа **Service** из Git-репозитория.
3. В качестве сборки выбрать **Dockerfile**, путь — `Dockerfile` в корне.
4. Порт сервиса — `8080`, health check — `GET /api/health`.
5. Задать переменные:

```env
NODE_ENV=production
PORT=8080
TRUST_PROXY=1
CORS_ORIGINS=https://mess.cvr.name,tauri://localhost,http://tauri.localhost,https://tauri.localhost
ANON_STATE_DB_PATH=/data/anon-state.sqlite
```

В Northflank добавьте persistent volume и смонтируйте его в `/data`. Если
бесплатный план не даёт volume, SQLite переживёт перезапуск процесса, но не
пересоздание сервиса.

`ANON_ROUTING_PRIVATE_KEY`, `ANON_PROXY_TARGETS` и `ANON_PUSH_WEBHOOK_URL`
нужны только для proxy/push; для обычного relay их можно не задавать.

6. Выдать сервису HTTPS-домен (Northflank даёт свой поддомен; можно
   привязать `relay-b.mess.cvr.name`).
7. Проверить:

```bash
curl -fsS https://<relay-b-host>/api/health
```

8. В сборке клиента указать:

```env
VITE_ANON_RELAY_URL=https://relay-a.example
VITE_ANON_RELAY_FALLBACK_URLS=https://<relay-b-host>
```

и пересобрать приложение.

Ограничения Northflank Sandbox:

- по документации платформа не предназначена для production;
- лимит ресурсов и 2 сервиса на аккаунт;
- без persistent volume пересоздание сервиса теряет SQLite-файл;
- если бесплатный лимит закончится, сервис может остановиться.

Это временное решение, пока нет второго VDS. Для постоянной работы лучше
Oracle Always Free или небольшой платный VPS.

## Вариант 2: Oracle Cloud Always Free (надёжнее)

Даёт бесплатную VM (по актуальным условиям — Arm Ampere, несколько OCPU и
RAM, плюс небольшие AMD-инстансы). Нужна карта для верификации, а инстансы
могут освобождать при простое. Это всё равно второй сервер, но без оплаты.

На VM:

```bash
sudo apt update && sudo apt install -y nodejs npm caddy
sudo useradd -r -m -d /opt/nova-relay nova
# скопировать репозиторий/образ, заполнить .env
sudo systemctl enable --now nova-relay
```

Caddy:

```caddyfile
relay-b.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Проверка — тот же `GET /api/health`, затем «Проверить relay» в приложении.
Файл базы по умолчанию лежит рядом с `server.js` (`anon-state.sqlite`);
каталог должен быть доступен на запись и включён в бэкап, если он нужен.

## Вариант 3: без второго хоста вообще

Если недоступен только сайт/лендинг, а VDS жив, поможет разделение:

- `server.js` — отдельный systemd-сервис;
- relay — на отдельном поддомене, например `relay.mess.cvr.name`;
- лендинг и его деплой не должны перезапускать relay.

Это не спасёт при падении всего VDS, но убирает самый частый сценарий:
сломанный деплой сайта или nginx, который задел relay.

## Что проверить после включения

1. `GET /api/health` на обоих relay.
2. Создать новый инвайт и убедиться, что в нём есть `standby` (в QR/ссылке).
3. Принять инвайт вторым устройством.
4. Остановить основной relay и отправить сообщение — оно должно уйти через
   резервный.
5. Поднять основной relay и убедиться, что новые сообщения снова идут через
   него.
6. Удалить контакт и проверить, что обе очереди удалены.

Пункты 4–6 требуют реального второго хоста; без него проверяется только
создание и опрос standby на тестовых транспортах.
