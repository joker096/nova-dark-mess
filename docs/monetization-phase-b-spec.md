## 1. Цель и что должно работать в конце

Фаза B превращает ручные продажи в платформу: рекламодатель платит в предоплаченный баланс,
адсервер сам выбирает креатив, считает показы, держит частотные лимиты, начисляет 50% админу
канала и отдаёт erid автоматически. Ручной остаётся модерация креативов и выплаты.

Gate из фазы A: ≥ 15 оплаченных размещений, медианный CPM ≥ $2, повторные заказы ≥ 5,
ноль нарушений маркировки. Если gate не пройден — эта фаза не начинается.

Критерии готовности фазы B:

| # | Критерий | Порог |
|---|---|---|
| 1 | Fill rate на каналах-партнёрах | ≥ 50% |
| 2 | Report rate (жалобы на рекламу) | ≤ 0.5% показов |
| 3 | Hide rate | ≤ 1% показов |
| 4 | Превышения caps (по логам сервера) | 0 |
| 5 | Точность начислений (сверка ledger ↔ оплаты) | 100%, расхождение 0 ₽ |
| 6 | Выплата админу от показа | ≤ 45 дней |
| 7 | Показы без erid | 0 |
| 8 | Утечки identity в рекламные таблицы | 0 (проверяется тестом схемы) |
| 9 | p95 задержки `/slot` | ≤ 120 мс |

## 2. Границы

**Входит:** спонсорский пост в ленте канала; серверные частотные лимиты; аукцион второй ценой;
ledger и 50% начисления; выплаты админам; автоматический erid через ОРД; дашборд админа v1;
продвигаемые каналы в каталоге; премодерация креативов; анти-фрод v1.

**Не входит (фаза C и позже):** self-serve кабинет рекламодателя, rewarded в мини-аппах,
внутренняя валюта, реклама в историях, спонсорские стикеры, ML-ранжирование, programmatic,
реклама в списке чатов. KYC рекламодателя не вводится ни в каком виде
(`moderation-and-ads-plan.md` §15.2).

## 3. Архитектура и границы сервиса

Адсервер — **отдельный, опционально self-hostable сервис**, не часть relay и не часть пути
доставки сообщений.

```
Client (Tauri/Web)                 Ad Service (новый)              Внешние
  ChannelScreen ── /slot ────────►  auction + caps + ledger ──────► ОРД API (erid, ЕРИР)
        │        ── /events ─────►  impressions / clicks / quality
        │                                │
        │                                ├──► PostgreSQL (только рекламные данные)
        └─ Settings → Ads (локально)     └──► Dashboard v1 (read-only web)

server.js (relay, presence, anon, premium) — не изменяется и не импортируется адсервером.
```

Обязательные свойства:

- **Изоляция:** ни одного `import` из `src/lib/crypto/`, `src/lib/social/`, `src/lib/anon/`,
  `src/lib/p2p/` в рекламном модуле; отдельный entrypoint и отдельный конфиг.
- **Feature flag:** `ADS_ENABLED` на сервере и `VITE_ADS_ENABLED` в сборке. При выключенном —
  клиент не делает ни одного запроса и не рендерит слот; сервер не поднимает маршруты `/api/ads/*`.
- **Fail closed:** нет ответа `/slot` за 800 мс или ошибка → рекламы нет, лента работает как
  обычно, ошибка не показывается пользователю.
- **Стек:** Node + Express (как `server.js`), PostgreSQL 15 (единственное место, где нужна
  транзакционность для ledger). SQLite допустима для пилота на одном инстансе, но ledger и caps
  должны быть совместимы с переездом без миграции логики.
- **Никаких данных relay:** адсервер не читает `receipts/`, не знает о presence, не видит очередей.

## 4. Модель данных

Канонические сущности — `moderation-and-ads-plan.md` §10; здесь только рекламные расширения и
то, чего там нет.

```sql
advertisers     (id, display_name, category, status, balance_cents, created_at)
campaigns       (id, advertiser_id, name, status, budget_cents, spent_cents,
                 pacing_mode, starts_at, ends_at, floor_cpm_cents)
creatives       (id, campaign_id, headline, body, cta_label, destination_url,
                 media_url, accent, lang, status, reject_reason,
                 erid, ord_id, erid_issued_at, erid_submitted_at)
channels        (id, admin_account_id, ads_enabled, floor_cpm_cents,
                 schedule_json, strictness, blocked_categories[], blocked_advertisers[],
                 status, created_at)
placements      (id, channel_id, creative_id, campaign_id, auction_id,
                 served_at, viewable_at, price_cents, revenue_channel_cents,
                 revenue_platform_cents, levy_cents, erid)
clicks          (id, placement_id, token_id, clicked_at, ua_hash, asn_hash)
cap_counters    (cap_key, creative_id, channel_id, day, impressions)
channel_ledger  (id, channel_id, placement_id, amount_cents, kind,
                 available_at, paid_out_at)
payouts         (id, channel_id, payout_account_id, period_start, period_end,
                 amount_cents, status, receipt_ref)
payout_accounts (id, channel_id, method, requisites_encrypted, created_at)  -- только для выплат
moderation_queue(creative_id, state, reviewer, decided_at, notes)
ord_outbox      (id, kind, creative_id, payload_json, attempts, last_error, sent_at)
```

Правила:

- `cap_counters` — единственная таблица с псевдонимом пользователя: `cap_key` = HMAC с суточной
  солью (см. §6), хранится максимум 35 дней, потом удаляется джобом.
- `ua_hash` / `asn_hash` — усечённый SHA-256 для анти-фрода; исходные User-Agent и IP не пишутся.
- `payout_accounts` — **единственное** место с реальными данными человека (реквизиты админа
  канала). Не содержит `user_id` мессенджера, не связывается с `channels.admin_account_id`
  ничем, кроме проверки владения каналом при создании записи (одноразовая процедура, §9).
- Ни одна рекламная таблица не имеет колонки с телефоном, именем, email, ключами, ID чата
  или ID контакта. Это проверяется тестом схемы (§12), а не договорённостью.

## 5. API

Версионированный префикс `/api/ads/v1`, JSON, лимит тела 32 КБ, rate limit по IP и по `cap_day`.

### 5.1. `POST /slot`

```json
{
  "channelId": "ch_...",
  "placement": "channel_feed",
  "lang": "ru",
  "country": "RU",
  "platform": "android",
  "capDay": "b7f3…",
  "capWeek": "1c9a…"
}
```

Ответ `200`:

```json
{
  "creative": {
    "id": "cr_...",
    "advertiserName": "…",
    "headline": "…",
    "body": "…",
    "ctaLabel": "…",
    "destinationUrl": "https://…",
    "accent": "#8ca6ff",
    "erid": "2Vfnx…",
    "disclosure": "ads.whyContext"
  },
  "placementId": "pl_...",
  "impressionToken": "it_...",
  "expiresAt": 1730000000000
}
```

- Пустой слот: `204 No Content`. Никакой «заглушки» вместо рекламы.
- Условия отказа: канал не активен, `ads_enabled = false`, креатив не прошёл модерацию или ерид,
  канал в чёрном списке рекламодателя, лимиты исчерпаны, ставки ниже floor, нет бюджета.
- `impressionToken` — подписанный сервером (HMAC), живёт 24 ч, одноразовый для клика.

### 5.2. `POST /events`

Батч до 50 событий, `keepalive`, без cookies:

```json
{"events": [
  {"type": "viewable", "placementId": "pl_...", "visibleMs": 1000},
  {"type": "click",    "token": "it_..."},
  {"type": "dismiss",  "creativeId": "cr_..."},
  {"type": "report",   "creativeId": "cr_...", "reason": "misleading"}
]}
```

- `viewable` засчитывается только при ≥ 50% пикселей ≥ 1 c (MRC), расчёт на клиенте,
  сервер валидирует минимальную длительность и дедуплицирует по `placementId`.
- `click` валидирует одноразовый токен; второй клик тем же токеном отбрасывается и попадает
  в анти-фрод журнал.
- Повторная отправка батча идемпотентна: у каждого события клиентский `eventId` (UUID v4).

### 5.3. Служебные

- `GET /api/ads/v1/health` — версия, `ads_enabled`, время последней успешной отправки в ОРД.
- `GET /api/ads/v1/channel/:id/settings` / `PUT` — настройки канала (только админ канала,
  авторизация по одноразовому токену владения, см. §9).
- `GET /api/ads/v1/dashboard/summary?channelId=&from=&to=` — агрегаты для дашборда v1.

## 6. Частотные лимиты и псевдонимы

Клиент не хранит постоянного идентификатора в рекламном контуре. При установке создаётся
случайный 32-байтный секрет в локальном хранилище (не покидает устройство), из него:

- `capDay = HMAC-SHA256(secret, "day:" + YYYY-MM-DD)`, `base64url`, первые 16 байт;
- `capWeek = HMAC-SHA256(secret, "week:" + ISO-year-week)`.

Сервер видит два несовместимых псевдонима и не может связать дни и недели между собой. Цена
такого решения: **кросс-недельные ограничения неисполнимы** — это осознанный компромисс, он
фиксируется в Privacy Policy. Внутри дня и недели лимиты жёсткие.

Лимиты (захардкожены на сервере, клиент не может их поднять):

| Лимит | Значение | Ключ счётчика |
|---|---|---|
| На пользователя в день | 3 показа | `capDay` |
| На пользователя в неделю | 8 показов | `capWeek` |
| Один креатив пользователю | 1 раз в 7 дней | `capWeek` + `creative_id` |
| На канал в день у пользователя | 1 показ | `capDay` + `channel_id` |
| Плотность в ленте | 1 реклама на 8–12 постов | решение клиента по позиции |
| Первые 24 ч после подписки | 0 показов | клиент, локально |
| После «Скрыть» | 0 показов рекламодателя 30 дней | клиент, локально |

Порядок проверки в `/slot`: канал → настройки/стоп-списки → budget → caps → brand safety →
аукцион → запись `placements` + инкремент счётчиков в одной транзакции.

## 7. Аукцион

- `eCPM = bidCpm × pCTR × qualityScore`; `pCTR` — только контекст (тематика канала, язык,
  страна, позиция), без профиля пользователя.
- Second price с reserve = `max(floor_cpm канала, min_quality_threshold)`; если победитель
  ниже reserve — пустой слот.
- `qualityScore` стартует с 1.0 и падает от hide rate и report rate креатива; ниже 0.4 креатив
  уходит на повторную модерацию автоматически.
- Pacing: дневной бюджет размазывается по часам, остаток не «сжигается» в конце дня.
- Понижение ставки рекламодателем вступает в силу со следующего часа (без гонок).
- Аукцион детерминирован при равных ставках: ничьи решает `creative_id`, чтобы тесты были
  воспроизводимы.

## 8. Экономика, ledger и выплаты

- Списывается с `advertisers.balance_cents` в момент **показа** (CPA и CPC — фаза C).
- Разбивка на `placements`: `price_cents = levy_cents + revenue_channel_cents +
  revenue_platform_cents`, где `levy_cents` = 3% (ПП № 1224), 50/50 — от остатка.
- `channel_ledger` — двойная запись: каждая строка ссылается на `placement_id`, обратной
  операции нет (исправления — только новой строкой `kind = 'adjustment'`).
- Holdback 30 дней: `available_at = served_at + 30 дней`; выплата — только по доступному остатку.
- Минимальная выплата $50; остаток переносится.
- Статусы `payouts`: `draft → approved → sent → confirmed` (или `failed`), каждое изменение
  пишется в аудит-лог с актором.
- Сверка: еженедельный отчёт «оплаты рекламодателей ↔ стоимость показов ↔ начисления каналам»;
  расхождение > 0 останавливает новые кампании до разбора (аналог стоп-условия фазы A).
- Возвраты за invalid traffic — на предоплаченный баланс рекламодателя, не деньгами.

## 9. Авторизация админа канала и дашборд v1

В продукте нет аккаунтов, поэтому владение каналом подтверждается локально:

1. Админ канала в приложении нажимает «Подключить монетизацию» → приложение генерирует
   одноразовый код (6 цифр + срок 10 минут) и показывает его.
2. Админ вводит код в веб-дашборде; сервер связывает браузерную сессию с `channels.admin_account_id`
   одноразово, дальше — сессионная кука `HttpOnly`, `SameSite=Strict`, срок 30 дней.
3. Реквизиты для выплат вводятся **только** там, шифруются на сервере (`payout_accounts`),
   в приложение не попадают и с сообщениями никак не связаны.

Дашборд v1 (read-only, отдельная сборка, не в клиенте):

- «Обзор»: подписчики, средний охват, ERR, доход за период, прогноз выплаты;
- «Реклама»: показы, viewable, eCPM, hide rate, report rate, топ креативов;
- «Настройки»: вкл/выкл рекламы, floor CPM, расписание, стоп-категории;
- «Выплаты»: начислено / в holdback / доступно / выплачено, документы.

Агрегаты с k-anonymity: группы меньше 100 человек не показываются; страны и языки — только
крупными корзинами. Никаких выгрузок «списком подписчиков».

## 10. Автоматический erid и ОРД

- erid запрашивается **при переводе креатива в `approved`**, до первого показа.
- Креатив без `erid` не может быть выдан в `/slot` — это проверка на уровне запроса, не
  только UI. Ошибка ОРД = креатив остаётся `pending_erid`, кампания не стартует.
- `ord_outbox` — исходящие операции (создание креатива, акт о распространении, отчёт): retry с
  экспоненциальной задержкой, `idempotency-key` = `creative_id`/`placement_id`, максимум 5 попыток,
  после — алерт.
- Акт о распространении формируется раз в сутки по завершённым `placements` с агрегатом охвата.
- erid выводится в карточке рядом с плашкой «Реклама»; правка текста креатива аннулирует erid
  и возвращает креатив в модерацию.
- Всё, что связано со сроками подачи в ЕРИР, фиксирует юрист; технически срок — параметр конфига.
- Реестр блогеров РКН: канал 10 000+ без подтверждения регистрации не может включить
  монетизацию (флаг `channels.status`).

## 12. Тесты и обязательные проверки в CI

- `src/lib/ads/` не импортирует `crypto/`, `social/`, `anon/`, `p2p/` — тест обхода импортов;
- схема БД: нет колонок с телефоном/именем/email/ID чата — тест миграций;
- caps: unit-тесты на границы (3-й показ проходит, 4-й — нет; недельный лимит; после «скрыть»);
- аукцион: детерминированные кейсы (reserve, quality score, равные ставки, pacing);
- ledger: property-тест «сумма разбивки = price», 1000 случайных размещений;
- erid: креатив без erid не выдаётся; ошибка ОРД не запускает кампанию; повторный вызов идемпотентен;
- e2e: канал с рекламой → показ → скрытие → слот не появляется 30 дней;
- сборка с `VITE_ADS_ENABLED=false` не делает запросов к `/api/ads/*` (проверка по логу сети в тесте);
- i18n-паритет для новых ключей.

## 13. Наблюдаемость и SLO

| Метрика | Цель / алерт |
|---|---|
| p95 `/slot` | ≤ 120 мс, алерт > 250 мс |
| Ошибки 5xx `/slot` | < 0.5%, алерт > 2% |
| Доля пустых слотов | < 50% на каналах-партнёрах |
| Показы без erid | 0, алерт на любом значении |
| Отставание `ord_outbox` | < 24 ч, алерт > 48 ч |
| Расхождение ledger при сверке | 0, любой случай — стоп кампаний |
| Задержка событий | p95 < 60 с от показа |

Логи: без IP в открытом виде, без User-Agent в открытом виде, без ID устройств. Retention
сырых событий — 90 дней, агрегатов — 24 месяца.

## 14. План работ

| Неделя | Работа | Выход |
|---|---|---|
| 1–2 | Схема БД, миграции, ledger, тесты инвариантов | данные и деньги считаются |
| 3–4 | `/slot`, caps, аукцион, pacing, feature flag, fail-closed | реклама выбирается сервером |
| 5–6 | `/events`, viewability, клик-токены, анти-фрод v1 | честные показы и клики |
| 7–8 | Интеграция с ОРД, erid, `ord_outbox`, акты | маркировка автоматическая |
| 9–10 | Дашборд v1, авторизация админа, настройки канала | админ видит доход сам |
| 11–12 | Выплаты, holdback, сверка, документы; пилот на 10–20 каналах | деньги доходят до админов |

Зависимости: серверный Channel Service (публичные каналы с серверной статистикой) — либо
минимальная его часть, либо явное решение, что охват на пилоте считается по данным клиента.

## 15. Риски фазы B

| Риск | Митигация |
|---|---|
| Рекламный модуль начинает «знать» о сообщениях | тест импортов, отдельный сервис, отдельная БД |
| Утечка псевдонима `capDay` → профиль | HMAC с суточной солью, удаление через 35 дней, запрет join с другими таблицами |
| Ошибка в ledger = потерянные деньги | двойная запись, property-тесты, ежедневная сверка, стоп-условие |
| ОРД недоступен → реклама без маркировки | fail closed, креатив не стартует без erid |
| Админ не может доказать владение каналом | одноразовый код из приложения + аудит всех подключений |
| Пустой слот ломает ленту | пустой слот = обычная лента, ошибок не видно |
| Сборка без рекламы ломается | CI-тест на отсутствие запросов и на полный набор функций |

## 16. Definition of Done

- [ ] адсервер развёрнут отдельно, `ADS_ENABLED` выключен по умолчанию;
- [ ] схема БД и тест «нет PII» зелёные;
- [ ] caps, аукцион, ledger, erid покрыты тестами §12 и они в CI;
- [ ] пилот на 10–20 каналах и 5–10 рекламодателях откручен без расхождений;
- [ ] первый автоматический erid прошёл путь «креатив → ОРД → показ → акт»;
- [ ] первый payout прошёл end-to-end быстрее 45 дней;
- [ ] клиент без рекламы полностью функционален (проверено сборкой и тестом сети).

## 17. Открытые вопросы

1. Channel Service: считаем охват по серверным данным или по клиентским событиям на пилоте.
2. PostgreSQL или SQLite на пилоте — и кто администрирует self-hosted инсталляции.
3. Какой ОРД даёт API, пригодное для `ord_outbox` (влияет на выбор в фазе A).
4. KYC на стороне платёжного провайдера: если он требует — используем предоплаченные коды,
   чтобы не вводить KYC в продукт (§15.2 модерационного плана).
5. Нужен ли отдельный публичный статус-эндпоинт для рекламодателя без аккаунта (по номеру
   заказа) — или всё через менеджера до фазы C.
