# Резервная очередь relay: как это работает

Дата: 2026-11-21. Документ описывает протокол standby-очереди, добавленный в
`src/lib/anon/session.ts`, `src/lib/anon/pairing.ts` и
`src/components/AnonymousMessengerScreen.tsx`.

## Зачем

Один VDS — единственная точка отказа: если он недоступен, недоступны и
основной relay, и сайт. Резервная очередь позволяет продолжить переписку через
второй независимый relay. Она не заменяет второй хост: без второго адреса
поведение остаётся прежним.

## Модель данных

У очереди появилось необязательное поле `standby`:

- в `AnonInvite` — второй адрес, который отправитель использует при ошибке
  основного;
- в `LocalInbox` — полноценная вторая очередь с собственными `queueId`,
  токенами, `signingKey` и `inviteToken`.

Резервная очередь:

- живёт на другом relay;
- использует тот же `recipientPublicKey`/`recipientPrivateKey`, поэтому
  получатель расшифровывает сообщения из любой из двух очередей;
- продолжает identity основного контакта: `identityKey` совпадает, а
  `identitySignature` подписывает ключ резервной очереди;
- не содержит вложенного `standby` (глубина ровно один уровень).

## Создание

`createInvitation` принимает необязательный `StandbyTarget`:

```ts
{ transport: InboxTransport; relayUrl: string }
```

Если он передан и адрес отличается от основного:

1. создаётся основная очередь;
2. создаётся резервная очередь с тем же TTL и отдельным PoW-челленджем;
3. резервная очередь получает тот же recipient-ключ и identity;
4. обе очереди попадают в инвайт и QR-код.

Если резервный relay недоступен в момент создания, приглашение всё равно
создаётся без `standby` — создание контакта не должно падать из-за резерва.

## Отправка

`sendContactMessage` и `sendContactOffer` работают так:

1. отправить в основной relay;
2. если запрос вернул ошибку/`null` — отправить в `invite.standby`;
3. если оба варианта не сработали, вернуть ошибку отправителю.

Файлы отправляются тем же путём с профилем `large`; каждый конверт может уйти
в резервную очередь, если основная недоступна.

## Получение

`checkInbox` создаёт по одной задаче на каждую очередь:

- основная очередь контакта;
- `contact.inbox.standby`, если она есть;
- то же для pending-инвайта.

Пакеты подтверждаются в той очереди, откуда пришли. Если основная очередь
ответила ошибкой, но резервная отдала пакеты, пользователь не видит красную
ошибку. Ошибка показывается только когда ни одна очередь контакта не
ответила.

## Ротация и failover

`rotateInbox` создаёт новую основную очередь на следующем relay и пытается
создать новую резервную на любом другом relay из списка. Если резерв создать
не удалось, ротация всё равно завершается.

`migrateInbox` отправляет новый инвайт каждому контакту:

- сначала в основную очередь контакта;
- при ошибке — в его резервную очередь.

Это важно, когда общий relay упал: новый адрес можно доставить через
резервный.

## Удаление

При удалении контакта удаляются обе очереди: основная и `standby`. Для каждой
используется тот же транспорт (direct, proxy или Tor), что и раньше.

## Включение

```env
VITE_ANON_RELAY_URL=https://relay-a.example
VITE_ANON_RELAY_FALLBACK_URLS=https://relay-b.example
```

Или через «Дополнительные relay» в настройках. Оба адреса должны быть
независимыми: разные VDS/провайдеры/регионы. Два процесса на одной машине не
переживут её падение.

## Ограничения

- `standby` появляется у новых инвайтов и у очередей после ротации. Старые
  контакты без резерва не получают его мгновенно.
- Если недоступны оба relay, переписка останавливается.
- К звонкам это не относится: signaling звонков идёт через WebSocket
  (`/api/signaling`) и TURN, а не через очередь сообщений; см.
  `docs/calls-signaling-turn.md`.
- В proxy-режиме оба relay должны быть доступны через proxy; при Tor оба
  адреса должны быть `.onion`.
- Инвайт с резервом длиннее, поэтому QR-код плотнее. При слишком длинном
  инвайте интерфейс покажет ошибку генерации QR, но ссылка продолжит работать.
