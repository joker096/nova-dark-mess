# Relay для Nova Dark Messenger: что нужно и как выбирать хостинг

Дата: 2026-11-21. Документ фиксирует решение по relay и требования к его
размещению, чтобы не путать его с WebRTC TURN или libp2p Circuit Relay.

## Коротко

- В приложении **свой HTTP relay** (`server.js`), а не TURN и не libp2p.
- Сообщения уже шифруются на клиенте; relay хранит только зашифрованные
  пакеты и метаданные очереди.
- **Cloudflare TURN, Metered Open Relay, ExpressTURN не подходят**: это
  серверы для медиатрафика WebRTC, у них нет API очередей сообщений.
- Рекомендуемый вариант: **собственный relay на VPS** (уже существующий
  сервер или бесплатная VM Oracle Cloud Always Free).
- Пользователю нужно дать возможность указать свой relay; в приложении это
  уже есть в расширенных настройках.

## Что такое relay в этом проекте

`server.js` — Node/Express-сервер, который принимает зашифрованные пакеты в
очередь и отдаёт их получателю. Основные endpoint'ы:

- `POST /api/anon/queues` — создать очередь;
- `POST /api/anon/enqueue` — положить пакет;
- `POST /api/anon/poll` — забрать пакеты;
- `POST /api/anon/ack` — подтвердить получение;
- `POST /api/anon/queues/delete` — удалить очередь.

Relay **не видит содержимое сообщений**: клиент шифрует пакеты до отправки.
Но он видит метаданные: queue id, IP клиента в direct-режиме, время и объём
трафика. Это описано в `docs/anonymity-audit.md` (finding A1).

Приложение принимает адрес relay в виде `https://...` или `.onion`. Адреса
вида `turn:...`, `stun:...` и libp2p multiaddr (`/ip4/.../p2p/...`) не
поддерживаются и не пройдут валидацию.

## Важное ограничение: один процесс и persistent storage

Очереди хранятся в `anonQueues` (`Map`) и сохраняются в SQLite-файл
`ANON_STATE_DB_PATH`. Поэтому:

- перезапуск процесса не теряет невыбранные сообщения;
- всё равно нельзя запускать несколько экземпляров relay за балансировщиком:
  у каждого будет своя SQLite-база и своя карта очередей;
- нельзя использовать serverless и бесплатные PaaS, которые «засыпают»:
  сон процесса останавливает приём сообщений;
- в контейнере нужен persistent volume для файла базы;
- нужен **один постоянно работающий процесс** с автоперезапуском.

Это главная причина, почему для relay нужен VPS или контейнер с volume, а не
Cloudflare Workers/Vercel/Netlify без отдельного хранилища.

## Резервная очередь на втором relay

В протоколе появилась необязательная резервная очередь. Если в сборке или
настройках указан второй независимый relay, новая очередь создаётся сразу на
двух хостах:

- основной адрес и `standby` попадают в инвайт (и в QR-код);
- отправитель сначала пишет в основной relay, а при ошибке — в резервный;
- получатель опрашивает обе очереди и подтверждает пакеты там, где они лежат;
- при ротации и failover резервная очередь пересоздаётся на другом хосте;
- при удалении контакта удаляются обе очереди.

Включается это только при наличии второго адреса:

```env
VITE_ANON_RELAY_URL=https://relay-a.example
VITE_ANON_RELAY_FALLBACK_URLS=https://relay-b.example
```

или через «Дополнительные relay» в настройках. `relay-b` должен быть на
другом провайдере/в другом регионе: два процесса на одном VDS падают вместе.

Ограничения текущего этапа:

- резервная очередь появляется у новых инвайтов и у очередей после ротации;
  старые контакты без `standby` не получают её мгновенно;
- если оба relay лежат, переписка всё равно останавливается;
- звонки используют отдельный WebSocket-signaling (`/api/signaling`) на этом
  же relay-процессе и настраиваемый TURN; см. `docs/calls-signaling-turn.md`.
  Падение relay обрывает установление нового звонка, но не текстовые очереди;
- proxy-режим должен уметь доходить до обоих relay; при Tor оба адреса должны
  быть `.onion`.

## Варианты размещения

| Вариант | Подходит | Ограничения |
|---|---|---|
| Свой VPS (Hetzner, Oracle, текущий `mess.cvr.name`) | **Да, рекомендуется** | Нужно администрирование, HTTPS и автозапуск |
| Oracle Cloud Always Free | Да, для старта | Нужна карта, регион может быть перегружен; одна VM, без масштабирования |
| Render / Railway / Fly.io free | Только для теста | Сон, лимиты, эфемерный диск, чужие IP в логах |
| Cloudflare перед своим relay | Как DDoS/HTTPS-прокси | Cloudflare видит IP пользователей; анонимности не добавляет |
| Cloudflare TURN / Metered / ExpressTURN | **Нет** | Другой протокол (WebRTC), нет очередей сообщений |
| Публичные libp2p relay | **Нет** | Проект не использует libp2p |

## Что нужно для собственного relay

### Минимальные ресурсы

- 1 vCPU, 1 ГБ RAM, 10 ГБ диска — с запасом для небольшого числа
  пользователей;
- Node.js 22.x (проект проверялся на Node 22);
- домен или поддомен, например `relay.example.com`;
- открытые 80/443 для HTTPS (или только 443, если сертификат выпускается
  отдельно);
- постоянный процесс: systemd, pm2 или Docker с `restart: always`.

### Переменные окружения

Обязательные для relay:

```env
PORT=8080
CORS_ORIGINS=https://app.example.com
ANON_STATE_DB_PATH=./anon-state.sqlite
```

Клиентская сборка:

```env
VITE_ANON_RELAY_URL=https://relay.example.com
```

`VITE_ANON_RELAY_URL` вшивается на этапе сборки. Если оставить его пустым,
приложение стартует в локальном режиме, а relay пользователь вводит вручную.

Опционально:

```env
ANON_ROUTING_PRIVATE_KEY=<32-byte base64url X25519 private key>
ANON_PROXY_TARGETS=relay1=https://relay.example.com
ANON_PUSH_WEBHOOK_URL=
ANON_REPORTS_DIR=./anon-reports
```

- `ANON_ROUTING_PRIVATE_KEY` нужен для proxy-режима: без него proxy-hop
  работает только с эфемерным ключом (developer-only).
- `ANON_PROXY_TARGETS` задаёт allowlist прокси на стороне relay.
- `ANON_PUSH_WEBHOOK_URL` — необязательный push-мостик; без него push нет.

### HTTPS и прокси

Рекомендуется Caddy перед Node: он сам получает сертификат Let's Encrypt и
проксирует запросы на `127.0.0.1:8080`.

```caddyfile
relay.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Node не должен слушать публичный интерфейс напрямую, если перед ним стоит
Caddy.

### Автозапуск

Systemd-юнит (пример):

```ini
[Unit]
Description=Nova anon relay
After=network.target

[Service]
WorkingDirectory=/opt/nova-relay
ExecStart=/usr/bin/node server.js
Restart=always
RestartSec=3
EnvironmentFile=/opt/nova-relay/.env
User=nova

[Install]
WantedBy=multi-user.target
```

### Проверка после запуска

```bash
curl -fsS https://relay.example.com/api/health
```

Затем в приложении: «Проверить relay» в настройках. Кнопка создаёт тестовую
очередь с TTL 60 секунд и проверяет прямой транспорт.

## Приватность и честные формулировки

- **Direct**: relay видит IP пользователя. Не называть этот режим полностью
  анонимным.
- **Proxy**: relay не видит IP, но proxy видит IP клиента. Нужен
  `ANON_ROUTING_PRIVATE_KEY` и allowlist.
- **Tor / .onion**: лучший вариант для скрытия IP, но медленнее; push при
  этом отключается.
- Свой relay не «знает ничего»: оператор видит метаданные. Преимущество в
  том, что оператор — вы, а не чужой бесплатный сервис с неизвестными
  логами.
- Логи relay стоит минимизировать и описать политику хранения. Не обещать
  отсутствие логов, если они включены на уровне reverse proxy или хостера.

## Решения, которые нужно принять

1. **Дефолт для сборки**: локальный режим (максимум приватности, больше
   трения) или свой relay по умолчанию (работает «из коробки», но relay
   видит IP).
2. **Proxy-режим**: включать ли его по умолчанию и кто будет оператором
   proxy. Без отдельного proxy IP пользователя видит relay.
3. **Onion-сервис**: нужен ли `.onion`-адрес вместе с HTTPS. Это лучший
   вариант для анонимности, но добавляет сложность.
4. **Резервирование**: один relay или несколько из `extraRelays`. Помнить,
   что очередь существует только на одном экземпляре; failover не переносит
   данные, а создаёт новую очередь.
5. **Политика логов и TTL**: сколько хранить abuse-отчёты и метаданные,
   какие логи отключить.

## Чего делать не нужно

- Подключать TURN-провайдера к текстовым сообщениям.
- Прописывать Cloudflare/Metered в «анонимное» приложение как обязательный
  relay.
- Разворачивать relay на serverless/PaaS с засыпанием.
- Запускать несколько реплик без внешнего хранилища очередей.
- Обещать, что relay не видит IP, оставаясь в direct-режиме.

## Следующий шаг

Подготовить пошаговый runbook для выбранной VM: пользователь, Node 22,
каталог, `.env`, systemd, Caddy, health-check, проверка из приложения. При
желании — добавить отдельный `.onion`-сервис для Tor.

До появления второго хоста резервная очередь в коде работает, но в продакшене
не активируется: второй адрес просто не задан. После деплоя второго relay
нужно пересобрать клиент с `VITE_ANON_RELAY_FALLBACK_URLS` и проверить
«Проверить relay» для обоих адресов.
