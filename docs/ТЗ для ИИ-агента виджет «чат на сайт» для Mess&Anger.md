# ТЗ для ИИ-агента: виджет «чат на сайт» для Mess&Anger

Nov 19, 2026

Цель: бесплатный встраиваемый чат-виджет для сайтов, который приводит в Mess&Anger владельцев сайтов и их посетителей. Владелец вставляет одну строку кода, посетители пишут ему с сайта без регистрации, а ответы владелец получает и отправляет из приложения мессенджера.

## Контекст и правила для агента

**Что уже есть.** Мессенджер на React + TypeScript (светлая и тёмная темы, чаты, звонки, профиль), лендинг https://mess.cvr.name/ (статичный HTML), позиционирование «как Telegram, но безопаснее», P2P-архитектура. Планируются боты и истории.

**Что делает виджет.** Он даёт сайту бесплатный живой чат, а мессенджеру три петли роста: владелец ставит приложение, чтобы отвечать; посетитель переходит из виджета в приложение; бренд «Работает на Mess&Anger» видят все посетители сайта.

**Правила работы агента:**

1. Перед началом изучи репозиторий: стек клиента, как устроены чаты, ключи, транспорт, авторизация, текущий backend. Если в проекте уже есть backend или relay, расширяй его. Rust (axum + tokio) и PostgreSQL в этом документе — предложение по умолчанию, а не требование.
2. Работай строго по этапам. Каждый этап завершай запускаемым результатом, тестами и коротким отчётом: что сделано, что не сделано, какие допущения.
3. Не ломай существующий функционал. Новый код живёт в отдельных модулях и папках (`packages/widget`, `server/site-gateway`, `app/features/sites`).
4. Если данных не хватает (нет схемы API, неясна модель ключей), остановись и задай вопрос. Не придумывай протокол молча.
5. Не добавляй трекеры, сторонние аналитические скрипты и внешние шрифты в виджет. Приватность сайта и посетителя — часть продукта.
6. Все строки интерфейса виджета выноси в словарь локализации (минимум ru и en).
7. Секреты (ключи подписи, токены) только через переменные окружения. В репозиторий их не коммить.

**Терминология.** *Сайт* — зарегистрированный владельцем сайт с `site_id`. *Гость* — анонимный посетитель с гостевой сессией. *Тред* — переписка одного гостя с одним сайтом. *Relay* — сервер, который хранит и пересылает зашифрованные сообщения, пока получатель офлайн. *Владелец* — пользователь мессенджера, привязанный к сайту.

## Этап 1. Виджет, гостевая сессия, relay, папка «Сайты»

Результат этапа: владелец регистрирует сайт в приложении, вставляет скрипт на страницу, гость пишет в виджете, а владелец отвечает из мессенджера. Если владелец офлайн, сообщения ждут на relay.

### 1.1 База данных

| Таблица | Поля |
| --- | --- |
| `sites` | `id` (uuid), `owner_user_id`, `name`, `domains` (список разрешённых origin), `site_pubkey`, `settings` (jsonb: цвет, приветствие, язык, позиция), `created_at` |
| `guests` | `id`, `site_id`, `guest_pubkey`, `first_seen_at`, `last_seen_at`, `blocked` |
| `threads` | `id`, `site_id`, `guest_id`, `status` (open, closed), `last_page_url`, `created_at`, `last_message_at` |
| `messages` | `id`, `thread_id`, `sender` (guest, owner, bot), `ciphertext`, `nonce`, `created_at`, `delivered_at`, `read_at` |

Индексы: `threads(site_id, last_message_at desc)`, `messages(thread_id, created_at)`. Миграции — в том формате, который уже используется в проекте.

### 1.2 API шлюза (`site-gateway`)

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/v1/sites` | Владелец (авторизован) создаёт сайт, получает `site_id` и сниппет |
| GET | `/v1/widget/config?site=ID` | Публичные настройки виджета (цвет, приветствие, `site_pubkey`) |
| POST | `/v1/guest/session` | Вход: `site_id`, `guest_pubkey`, решение proof-of-work. Ответ: короткий `guest_token`, `thread_id` |
| WS | `/v1/guest/ws` | Отправка и получение сообщений, typing, подтверждения доставки |
| GET | `/v1/guest/history?after=` | История треда при повторном визите |
| WS события владельцу | `thread.new`, `message.new`, `thread.closed` | Доставляются через существующий канал мессенджера |

Все ответы — JSON. Ошибки в едином формате `{code, message}`. Опиши API схемой OpenAPI в `docs/api/site-gateway.yaml`.

### 1.3 Шифрование

- Сервер видит только шифротекст и метаданные (время, размер, `thread_id`).
- Гость генерирует пару X25519 в браузере (libsodium-wasm или WebCrypto). Сообщения: ECDH с `site_pubkey` + XChaCha20-Poly1305.
- Если в проекте уже есть схема E2E и мультиустройственных ключей, переиспользуй её. Секретный ключ сайта хранится у владельца и доступен на всех его устройствах. **Открытый вопрос к автору проекта:** как в мессенджере сейчас синхронизируются ключи между устройствами; агент обязан уточнить это до реализации.
- Приватный ключ гостя живёт в `localStorage` внутри iframe виджета (изолированный origin), чтобы код сайта не мог его прочитать.

### 1.4 Виджет (`packages/widget`)

- Скрипт-загрузчик до 2 КБ gzip: читает `data-site`, создаёт кнопку-лаунчер в Shadow DOM и по клику грузит iframe чата. Сам чат: TypeScript без фреймворков, цель до 30 КБ gzip.
- Связь iframe и страницы — только `postMessage` с явной проверкой `origin` в обе стороны. Странице передаётся только URL и заголовок.
- Состояния: подключение, онлайн, владелец не в сети («Ответим, как только вернёмся»), ошибка сети с автоповтором, индикатор набора, статусы «отправлено / доставлено / прочитано».
- Светлая и тёмная темы (по умолчанию по `prefers-color-scheme`), акцентный цвет из настроек сайта, адаптив под телефон (на маленьких экранах — полноэкранный режим). Визуально ориентируйся на стиль мессенджера.
- Доступность: фокус-ловушка, закрытие по Esc, `aria-live` для новых сообщений, навигация с клавиатуры.
- Хранилище браузера оборачивай в `try/catch` (в приватном режиме оно бывает недоступно): без него виджет работает как одноразовая сессия.

### 1.5 Приложение (`app/features/sites`)

1. Пункт «Сайты» в навигации и папка «Сайты» в списке чатов.
2. Мастер «Подключить сайт»: название, домены, цвет, приветствие, готовый сниппет с кнопкой «Копировать», кнопка «Проверить установку» (сервер видит первый запрос конфига с разрешённого домена).
3. Список тредов по сайту с бейджем непрочитанных. Каждый тред показывает «Гость с example.com, страница /pricing».
4. Экран чата с гостем на том же компоненте переписки, что и обычные чаты, с дополнительными действиями: закрыть тред, заблокировать гостя, быстрые ответы (шаблоны текста).
5. Push и внутриприложенческие уведомления о новом треде и сообщениях; настройка «не беспокоить» по расписанию.
6. Полный комплект состояний экранов: пусто («пока никто не написал» + инструкция), загрузка, ошибка, сайт не подтверждён.

### 1.6 Relay

- Хранит зашифрованные сообщения и доставляет их владельцу при подключении; доставка «минимум один раз» с подтверждением (`ack`) и дедупликацией по `message.id`.
- Срок хранения недоставленных — 30 дней (конфиг), после доставки и подтверждения — удаление с сервера по настройке сайта.
- Лимиты: размер сообщения до 4 КБ текста, вложений на этапе 1 нет.

### 1.7 Проверка origin

Сессия гостя создаётся только если заголовок `Origin` входит в `sites.domains`. Для `localhost` — только в режиме разработки.

### 1.8 Демостраница

Отдельная страница `examples/basic.html` с вставленным сниппетом: по ней принимается этап.

### Критерии приёмки этапа 1

- [ ] Сайт регистрируется, сниппет на демо-странице показывает кнопку чата.
- [ ] Сообщение гостя появляется у владельца в папке «Сайты» за до 2 секунд при онлайне и доставляется после возврата из офлайна.
- [ ] Ответ владельца появляется у гостя; после перезагрузки страницы история сохраняется.
- [ ] Сервер нигде не хранит и не логирует текст сообщений в открытом виде (проверить по дампу БД и логам).
- [ ] Сессия с неразрешённого домена отклоняется.
- [ ] Виджет работает в Chrome, Firefox, Safari (macOS и iOS) и на ширине 320 px.
- [ ] Размер загрузчика и чата укладывается в цели из пункта 1.4.

## Этап 2. Переход гостя в мессенджер, брендинг, метрики

Результат этапа: гость может перенести переписку в приложение и стать пользователем, а ты видишь, сколько посетителей прошло этот путь. Это ключевой этап для роста: без него виджет приводит только владельцев.

### 2.1 Кнопка «Продолжить в мессенджере»

- Появляется в виджете после первого сообщения гостя. Текст: «Получите ответ в мессенджере, даже если закроете сайт». Не навязывать: это необязательный шаг, чат работает и без него.
- По клику сервер выпускает одноразовый `handoff_token` (срок 7 дней, аналогичный путь привязки уже может быть в проекте: проверь и переиспользуй). Ссылка: `https://mess.cvr.name/c/<handoff_token>#<ключ>`.
- **Ключ гостя передаётся только в фрагменте ссылки** (часть после `#` не отправляется на сервер). Так E2E сохраняется, а пользователь не теряет историю.
- На компьютере вместо ссылки показывается QR-код с той же ссылкой; на телефоне — кнопка.

### 2.2 Страница `/c/<token>` на лендинге

1. Если приложение установлен, открывается оно (universal link или схема, которую уже использует приложение).
2. Если нет, страница показывает: «Вас ждёт ответ от *Название сайта*», кнопки скачивания для платформы посетителя (ссылки бери из уже существующего `releaseUrls.js`) и вариант «Открыть в браузере», если есть веб-клиент.
3. После регистрации или входа тред гостя привязывается к его аккаунту, токен инвалидируется.
4. В приложении гость видит обычный чат «Название сайта» с полной историей; владелец продолжает отвечать в том же треде. Виджет на сайте дальше показывает «Переписка продолжается в мессенджере».

### 2.3 Брендинг

- В низу виджета строка «Работает на Mess&Anger» со ссылкой `https://mess.cvr.name/?utm_source=widget&utm_medium=referral&utm_campaign=<site_id>`.
- Строка рисуется внутри iframe, чтобы её нельзя было скрыть CSS сайта.
- В `sites.settings` флаг `hide_branding` (по умолчанию `false`). В этот этап владелец его не меняет; флаг нужен для будущего платного тарифа.
- Добавь на лендинг раздел «Для сайтов»: что это, скриншот виджета, сниппет для копирования, ответы на вопросы про приватность. Добавь в `privacy.html` описание того, какие данные виджет собирает и как хранится переписка.

### 2.4 Метрики

Считай только агрегаты по сайту и дню. IP-адреса, user-agent и текст сообщений в метриках не хранить. Таблица `site_stats_daily(site_id, date, ...)`:

| Событие | Когда считается |
| --- | --- |
| `loaded` | Скрипт запросил конфиг сайта |
| `opened` | Гость открыл чат |
| `first_message` | Гость отправил первое сообщение в треде |
| `owner_replied` | Владелец ответил в треде |
| `handoff_shown` | Гость увидел кнопку перехода |
| `handoff_clicked` | Гость нажал кнопку или открыл QR-ссылку |
| `handoff_completed` | Тред привязан к аккаунту мессенджера |

Показывай владельцу в приложении экран «Статистика сайта» (за 7 и 30 дней). Для автора проекта сделай закрытую админ-страницу с воронкой `loaded` → `opened` → `first_message` → `handoff_clicked` → `handoff_completed` по всем сайтам. Ориентир по конверсии гостя в пользователя приложения — 2–5% от гостей, написавших хотя бы одно сообщение. Это ориентир, а не требование к коду.

### Критерии приёмки этапа 2

- [ ] Гость на телефоне попадает в свой тред в приложении не более чем за 3 нажатия от кнопки в виджете (если приложение уже установлено).
- [ ] История переписки не теряется; сервер не видит ключ гостя (проверь по логам nginx и сервера: фрагмент не попадает ни в один запрос).
- [ ] Повторное использование токена и просроченный токен отклоняются с понятным сообщением.
- [ ] Все события из таблицы выше записываются; в БД метрик нет персональных данных.
- [ ] Ссылка брендинга не скрывается стилями страницы-хоста.

## Этап 3. WordPress-плагин и публичные ссылки-визитки

Результат этапа: виджет ставится на WordPress-сайт за одно нажатие из каталога плагинов, а каждый пользователь мессенджера может разместить ссылку «Написать мне» в соцсетях и подписях.

### 3.1 WordPress-плагин `mess-chat`

Плагин на PHP (совместимый с PHP 7.4+ и 8.x, WordPress 6.x), без зависимостей от Composer и без требований к хостингу сверх базовых PHP и MySQL. Лицензия GPL-2.0+ (требование каталога WordPress.org).

1. **Структура:** `mess-chat.php` (заголовок плагина), `includes/settings.php`, `includes/frontend.php`, `uninstall.php`, `readme.txt`, `languages/` (ru\_RU, en\_US), `assets/` (иконка и баннер для каталога).
2. **Страница настроек** («Настройки → Mess Chat») на Settings API: поле `Site ID`, включение и отключение виджета, выбор языка и позиции, кнопка «Подключить через Mess&Anger». Кнопка открывает `https://mess.cvr.name/connect?return=<адрес настроек>` и после подтверждения в приложении возвращает `site_id` в настройки (без ручного копирования).
3. **Подключение скрипта:** `wp_enqueue_script` в подвале с атрибутами `async` и `data-site`; только на публичной части сайта, не в админке и не в предпросмотре конструктора.
4. **Безопасность кода плагина:** входные данные через `sanitize_text_field` и свои sanitize-колбэки, вывод через `esc_attr` и `esc_html`, проверка `current_user_can('manage_options')`, nonce на формах, прямой доступ к файлам запрещён (`defined('ABSPATH') || exit;`).
5. **Приватность:** через `wp_add_privacy_policy_content` добавь текст о том, что виджет передаёт на сервер Mess&Anger. Ничего не загружать с сторонних доменов, кроме скрипта виджета.
6. **Режим first-party** (опция в настройках): плагин сам проксирует загрузчик с домена сайта (см. раздел «Безопасность», пункт обхода блокировщиков). Запрос к конфигу кэшируется в `transient` на 1 час.
7. **Каталог:** `readme.txt` по формату WordPress.org (описание, FAQ, скриншоты, changelog), отдельно подготовь проверку в Plugin Check перед загрузкой. Саму отправку в каталог делает автор проекта вручную.

### 3.2 Инструкции для других платформ

Страница `https://mess.cvr.name/docs/widget` с короткими инструкциями для Tilda, Wix, Shopify, Joomla и обычного HTML: куда вставить сниппет, как проверить установку, как удалить. Для каждой платформы статичный блок с копируемым кодом.

### 3.3 Публичные ссылки-визитки

Пользователь включает публичный профиль, и у него появляется страница `https://mess.cvr.name/u/<username>`. Внутренне это тот же «сайт» из этапа 1 с полем `sites.kind = 'profile'`: переиспользуй виджет, гостевые сессии и relay, не пиши отдельный протокол.

- **Страница:** имя, аватар, короткое описание, кнопка «Написать» (открывает чат в браузере для гостя) и кнопка «Открыть в приложении» для уже зарегистрированных. Страница рендерится на сервере (не в браузере) с Open Graph-тегами, чтобы ссылка красиво выглядела в соцсетях и мессенджерах.
- **Имя пользователя:** `[a-z0-9_]{3,32}`, уникальное, без зарезервированных слов (`admin`, `support`, `api`, `docs`, `login`, имя бренда).
- **Приватность по умолчанию:** профиль выключен, после включения страница `noindex`. Индексация поисковиками — отдельный переключатель. Пользователь может выключить профиль в любой момент, ссылка перестаёт работать.
- **В приложении:** экран «Моя ссылка» (выбор имени, проверка занятости в реальном времени, кнопки «Копировать», «Показать QR», «Поделиться» через системный меню шаринга).
- **Правила для гостей:** лимит на число новых тредов в сутки, кнопка «Пожаловаться» на странице, владелец профиля может ограничить «писать могут только зарегистрированные».
- **Диплинк:** `mess.cvr.name/u/<username>` открывает приложение на этом профиле, если оно установлено.

### Критерии приёмки этапа 3

- [ ] Плагин устанавливается на чистый WordPress 6.x, подключается через кнопку и показывает чат на сайте; при отключении и удалении не оставляет данных в базе (`uninstall.php`).
- [ ] Plugin Check не показывает ошибок; в админке и предпросмотре виджет не появляется.
- [ ] Плагин работает на хостинге только с PHP и MySQL, без дополнительных расширений.
- [ ] Ссылка `/u/<username>` открывается без регистрации, гость пишет, владелец отвечает из приложения.
- [ ] При выключенном профиле страница отдаёт 404; при включенном по умолчанию стоит `noindex`.
- [ ] Занятые и зарезервированные имена нельзя выбрать.

## Этап 4. Боты в виджете, «Войти через Mess», уведомления от сайтов

Результат этапа: сайты получают автоответчики и ботов, а также бесплатную авторизацию и уведомления через мессенджер вместо SMS. Это уже отдельный продуктовый слой, начинай его только после приёмки этапов 1–2.

### 4.1 Боты в виджете

**Зависимость.** Платформа ботов мессенджера планируется отдельно. Если она уже есть, подключи ботов к сайту через её API. Если нет, сделай минимальный вебхук-вариант ниже и позже перенеси его на общую платформу.

1. В настройках сайта появляются `bot_webhook_url` и `bot_secret`. Шлюз шлёт события `thread.new` и `message.new` на этот URL как HTTPS POST с подписью HMAC-SHA256 в заголовке `X-Mess-Signature` и меткой времени (окно 5 минут, защита от повтора).
2. Бот отвечает запросом `POST /v1/bot/threads/{id}/messages` с токеном бота. Поддержи текст и кнопки быстрых ответов (до 6 штук); в виджете они рисуются под сообщением.
3. Встроенный FAQ-бот для тех, кто не хочет писать код: владелец в приложении задаёт пары «вопрос → ответ» и ключевые слова. Если совпадения нет, виджет предлагает «Позвать человека» и передаёт тред владельцу с уведомлением.
4. Автоответ вне рабочего времени: владелец задаёт расписание и текст, виджет показывает его вместо стандартного «Ответим, как только вернёмся».

**Честность про E2E.** Если к сайту подключён внешний бот, ему нужны открытые сообщения, и сквозное шифрование гость-владелец для этого треда недоступно. Виджет обязан показать гостю явную плашку: «Этот чат обрабатывает бот сайта, сообщения видны ему». В настройках сайта владелец явно включает «режим бота» и видит это предупреждение. Встроенный FAQ-бот работает на устройстве владельца и шифрование не ломает; подумай, возможно ли это при офлайне владельца, и зафиксируй решение в отчёте.

### 4.2 «Войти через Mess»

Стандартный OAuth 2.0 (authorization code + PKCE), как у «Войти через Google», только без паролей.

1. Сайт открывает `https://mess.cvr.name/oauth/authorize` с параметрами `client_id` (это `site_id`), `redirect_uri`, `state`, `code_challenge`, `scope`.
2. Пользователь получает запрос в приложении: «Сайт *Название* хочет войти в ваш аккаунт», список запрашиваемого, кнопки «Разрешить» и «Отмена». Для пользователя без приложения — вход по QR-коду или коду из бота.
3. Сервер возвращает одноразовый `code` (живёт 60 секунд) на `redirect_uri`; бэкенд сайта меняет его на токен через `POST /oauth/token`.
4. В ответе — ID-токен (JWT, подпись EdDSA или ES256, публичные ключи на `/.well-known/jwks.json`). Поля: `sub` (псевдонимный идентификатор, свой для каждого сайта), `name`. Телефон, email и другие данные не передаются.
5. `redirect_uri` сверяется с доменами сайта точно, без масок. Код одноразовый, `state` обязателен, PKCE обязателен.
6. В приложении экран «Подключённые сайты» с кнопкой «Отключить».
7. Для разработчиков сайтов: страница `/docs/login` с примером на PHP и Node.js и готовая кнопка «Войти через Mess» (светлая и тёмная).

### 4.3 Уведомления от сайтов в мессенджер

- Только для пользователей, которые вошли через Mess и явно разрешили scope `notify`. Без разрешения сайт не может написать первым.
- `POST /v1/notify` с токеном сайта: `sub`, заголовок, текст (до 500 символов), необязательная ссылка на домен сайта. Сообщения приходят в отдельный чат с названием сайта, без возможности ответить.
- Лимиты: до 5 уведомлений в сутки на пользователя от одного сайта. Пользователь может заглушить сайт одним нажатием; повторные жалобы блокируют сайт.

### Критерии приёмки этапа 4

- [ ] Тестовый вебхук-бот получает подписанное событие и отвечает; неверная или просроченная подпись отклоняется.
- [ ] В треде с внешним ботом гость видит предупреждение о видимости сообщений.
- [ ] FAQ-бот отвечает на настроенные вопросы и передаёт тред человеку по кнопке.
- [ ] Полный цикл «Войти через Mess» проходит на тестовом сайте; подмена `redirect_uri`, повтор `code`, старый `code` и отсутствие `state` отклоняются.
- [ ] Разные сайты получают разные `sub` для одного и того же пользователя.
- [ ] Уведомления без разрешения `notify` не доставляются; лимиты и блокировка работают.

## Безопасность, антиспам, обход блокировщиков

Этот раздел применяется ко всем этапам. Без антиспама виджет станет целью для рассылок, без обхода блокировщиков — бесполезен на значительной части сайтов.

### Антиспам

| Мера | Как реализовать |
| --- | --- |
| Proof-of-work при создании гостевой сессии | hashcash-подобная задача, сложность растёт при подозрительной активности с одного IP; для обычного посетителя незаметна |
| Лимиты частоты | Сессии: до 10 в час с IP на сайт. Сообщения: до 20 в минуту от гостя. Один открытый тред на гостя и сайт. Числа — стартовые, вынеси их в конфиг |
| Два уровня лимитов | `limit_req` в nginx перед шлюзом и лимиты в коде шлюза по `site_id` и `guest_id` |
| Капча как запасной вариант | Только самостоятельно развёрнутая, без Google reCAPTCHA и других трекеров. Включать только при атаке |
| Блокировка владельцем | Кнопка «Заблокировать гостя» в треде: сервер отклоняет новые сессии этого ключа и хеша IP на этом сайте |
| Блокировка сайтов платформой | Админ-инструмент для автора проекта: отключить сайт или владельца по жалобам (фишинг, спам) |
| Жалобы | Кнопка «Пожаловаться» для гостя в виджете и для пользователя в приложении |

### Защита от атак на виджет и приложение

- Сообщения гостя показывай только как обычный текст (без HTML и Markdown) и в виджете, и в приложении владельца. Ссылки становятся кликабельными только с предупреждением «Вы переходите на внешний сайт» и с `rel="noopener noreferrer"`.
- Строгий CSP для iframe чата: `default-src 'none'`, скрипты только свои, `connect-src` только на шлюз. `frame-ancestors` выдавай динамически из `sites.domains`, чтобы чужие сайты не встраивали чат ключа другого сайта.
- Без cookie: токены живут в памяти и в `localStorage` iframe. Учти, что браузеры разделяют хранилище сторонних iframe по сайту-хозяину: гость на разных сайтах будет разным гостём, и это нормально.
- Подпись токенов — ключи из переменных окружения с возможностью ротации (поле `kid` в токене).
- В CI: `cargo audit` и `npm audit` (или эквиваленты выбранного стека), линтеры, запрет коммита секретов.

### Приватность

- Не создавай ключи и записи в хранилище браузера, пока гость не открыл чат. Кнопка-лаунчер до клика ничего не хранит и не отправляет, кроме запроса конфига.
- В виджете кнопка «Удалить мои данные»: удаляет гостя, его тред и сообщения на сервере и локальные ключи.
- IP не хранить. Для лимитов используй хеш IP с ежедневно меняющейся солью. В логах нет текста сообщений и полных IP.
- Обнови `privacy.html` на лендинге: какие данные собирает виджет, сроки хранения, права гостя, различие между зашифрованным чатом и режимом бота.

### Обход блокировщиков рекламы и трекеров

Чат-виджеты часто попадают в фильтры по имени домена и пути. Решение — вести себя как часть самого сайта, а не как сторонний сервис.

1. **First-party прокси.** Владелец может отдавать загрузчик и запросы виджета с своего домена. Для nginx дай готовый фрагмент конфигурации (`location /m/ { proxy_pass ...; }`), для WordPress — режим в плагине (этап 3), который проксирует запросы через PHP и кэширует статику.
2. **Нейтральные имена.** В путях, именах файлов, классах и параметрах не используй слова «chat», «widget», «track», «аналитика», «ads», «beacon». Разработчику должно быть удобно, поэтому выбери одно такое нейтральное имя модуля и собери всё под ним.
3. **Метрики на стороне сервера.** События из этапа 2 считай по запросам к шлюзу (запрос конфига, создание сессии, первое сообщение), а не клиентскими маячками, которые фильтры блокируют первыми.
4. **Тесты с реальными блокировщиками:** uBlock Origin, AdGuard, Brave Shields, списки EasyList и EasyPrivacy. Используй тот же стенд тестов, как в проекте баннера для блокировщиков, если он уже есть. Результат запиши в таблицу: блокировщик, режим (сторонний домен или first-party), работает ли виджет.
5. **Честный фолбэк.** Если виджет всё равно заблокирован, сайт может показать простую ссылку `/u/<username>` вместо виджета — это обычная страница, её фильтры не трогают.

### Критерии приёмки

- [ ] Скрипт, генерирующий тысячу сессий с одного IP, блокируется лимитами и PoW (нагрузочный тест).
- [ ] Сообщение с `<script>` и HTML-разметкой отображается как текст и не выполняется ни у гостя, ни у владельца.
- [ ] Чужой сайт не может встроить чат в iframe (проверь заголовок `frame-ancestors`).
- [ ] Таблица тестов с блокировщиками заполнена, в first-party режиме виджет работает при включённом uBlock Origin со стандартными списками.
- [ ] До клика по лаунчеру в хранилище браузера ничего не пишется; «Удалить мои данные» работает.
- [ ] В базе и логах нет открытого текста сообщений и полных IP.

## Порядок работы, тесты и открытые вопросы

Агент работает этапами по порядку и не начинает следующий, пока не закрыты критерии приёмки текущего. Раздел «Безопасность» применяется на каждом этапе, а не в конце.

### Порядок этапов

1. **Подготовка.** Изучи репозиторий, ответь себе на открытые вопросы ниже (там, где ответ есть в коде) или задай их автору. Подготовь схему API (OpenAPI) и миграции до написания кода.
2. **Этап 1.** Сначала backend (БД, шлюз, relay), потом виджет, потом экраны приложения, потом демо-страница и полный прогон критериев.
3. **Работа на своих сайтах.** После этапа 1 подключи виджет на свои сайты (cvr.name, mess.cvr.name, prostocartridge.ru, photolessons.org) и несколько недель проверяй на реальных посетителях. Это первые кейсы для лендинга.
4. **Этап 2.** Только после этого добавляй переход в мессенджер и метрики.
5. **Этап 3**, затем **этап 4**. Боты и «Войти через Mess» не начинай, пока в метриках этапа 2 нет реальных переходов гостей в приложение: если их нет, нужно дорабатывать воронку, а не наращивать функционал.

### Тесты

- **Backend:** модульные тесты логики лимитов, токенов, OAuth, подписей вебхуков; интеграционные тесты с реальной БД.
- **Виджет:** модульные тесты шифрования и состояний; сквозные тесты в Playwright в Chromium, Firefox и WebKit: гость пишет → владелец получает → отвечает → гость видит ответ.
- **Нагрузка:** тест на 1000 одновременных WebSocket-соединений и рост памяти/задержки в отчёт. Цифра — ориентир, агент уточняет её по серверу автора.
- **Безопасность:** проверки из критериев каждого этапа (XSS, подмена `redirect_uri`, повтор токена, встраивание в чужой сайт) оформлены как автоматические тесты.

### Отчёт агента по этапу

В конце каждого этапа агент пишет `docs/reports/stage-N.md`: что сделано; какие критерии пройдены с доказательством (команда теста, скриншот); что не сделано и почему; допущения; следующий шаг. Критерий без доказательства считается не пройденным.
