# Anonymous Queue Relay Protocol (v1)

This document specifies the first implementable version of the anonymous
delivery layer. It is a draft and must be reviewed before production use.

Status (2026-11-17): v1 scaffold. It describes the current uncommitted
implementation and calls out where that implementation does not meet the
target. Do not use in production until the blockers in §8 are resolved.

## 1. Entities

- **Client**: sender or recipient of messages.
- **Relay**: thin, stateless-ish store-and-forward service for fixed-size
  encrypted packets.
- **Proxy** (phase C): optional hop that hides sender IP from the relay.

## 2. Identities and queues

- There are no global user accounts.
- Target: an invite creates one direction of a contact. Each party owns a
  one-way inbox queue; no queue ID is shared between directions.
- Current implementation: `src/lib/anon/pairing.ts` creates an independent
  inbox queue per party. The inviter shares an invite (`queueId`, `senderToken`,
  `signingKey`, `recipientPublicKey`, `relayUrl`, `expiresAt`, optional `pow`,
  optional `identityKey` — the public signing key of that inbox's first queue,
  kept across relay rotation and used only for local block lists and contact
  recognition — plus optional `identitySignature`, an Ed25519 signature by
  `identityKey` over the current queue signing key and a fixed domain string).
  A first invite can omit the signature because its identity is its own queue
  key; a rotated invite is honoured only when the signature verifies, otherwise
  the peer falls back to the queue key. The invitee
  creates its own inbox and sends a sealed `contact_offer` containing its invite
  to the inviter's queue. Each side then writes to the peer's inbox.
- Each queue record has:
  - `queueId`: public-ish routing identifier, 16 random bytes, hex, prefixed
    with `q_`.
  - `senderToken`: secret presented by senders when enqueuing.
  - `recipientToken`: secret presented by recipients when polling/acking.
  - `signingPublicKey`: Ed25519 public key used to verify queue commands.
  - `pow`: optional first-contact proof-of-work challenge; `powUsed` marks it
    consumed after the first accepted enqueue.
- The queue creator generates an Ed25519 key pair, sends `signingPublicKey` to
  the relay, and puts the private `signingKey` in the invite. The relay stores
  only the public key. Legacy queues created without a `signingPublicKey` remain
  unsigned for compatibility.
- If the invite carries a `pow` challenge, the sender solves it once and
  includes the solution in the first `enqueue`. The relay verifies the solution
  and marks the challenge used; later sends on that queue do not need PoW.
- The raw relay API still supports a legacy single queue with both tokens; using
  it for both directions reintroduces linkability. Pairing is the supported path.
- Pairing removes the shared queue ID, but the relay/proxy can still correlate
  timing. Use proxy/Tor for IP separation.
- Commands are authorized by the relevant bearer token **and** (for new queues)
  an Ed25519 signature from the queue signing key.

## 3. Packet format

All relay-bound packets use one of the fixed profiles:

- `small`: 4096 bytes
- `standard`: 16384 bytes
- `large`: 65536 bytes

Binary layout:

```text
[0..3]   uint32 big-endian plaintext length
[4..]    plaintext bytes
[rest]   random padding
```

The plaintext currently written by `src/lib/anon/session.ts` is the JSON form
of a sealed-sender envelope (`ephemeralPublicKey` plus AES-GCM `encrypted`
fields), encoded to UTF-8 and padded into the fixed profile. The relay sees
only the fixed-size outer bytes. `AnonPacket` in `types.ts` is relay-side
metadata, not the encrypted payload.

`encodeFixedFileChunks` splits an already-encrypted file byte stream into
profile-sized packets; `decodeFixedFileChunks` validates and reassembles them.
Chunk indexes and counts are client-side transfer metadata and must travel
inside the encrypted application payload when sent over the relay. Receipts
and in-band control payloads can use `encodeFixedPacket` to get the same
fixed-size framing. HTTP relay operations such as ACK remain variable-length
control traffic in v1 and are not covered by this packet framing.

## 4. Relay commands

### create_queue

`POST /api/anon/queues` creates a queue with TTL. Both sender and recipient
tokens are generated by the relay and returned once to the creator; the relay
stores only their SHA-256 hashes. The creator keeps the recipient token and
shares the sender token through the invite. Current v1 returns both tokens in
the same response. The direct endpoint reveals the creator IP to the relay.

The creator may include `signingPublicKey` (32-byte Ed25519 public key,
base64url). The relay stores it with the queue. The creator keeps the matching
private `signingKey` and puts it in the invite. Omitting `signingPublicKey`
creates a legacy unsigned queue; an invalid key returns `INVALID_SIGNING_KEY`.
The direct create response does not return the signing key because the creator
already holds it.

The creator may also include a `pow` challenge:
`{challenge: base64url, difficulty: 1..24}`. The relay binds it to the queue
and requires a matching `pow` solution on the first enqueue. Invalid difficulty
or malformed challenge returns `INVALID_POW_CHALLENGE`.

`ProxyAnonTransport.createQueue` generates the signing key pair locally, sends
`signingPublicKey` (and optional `pow`) inside the sealed `create` command, and
receives the queue credentials in a response sealed to an ephemeral reply key.

### Signed commands

For queues with a `signingPublicKey`, `enqueue`, `poll`, `ack`, and
`delete_queue` must include:

- `signature`: Ed25519 signature, base64url;
- `signedAt`: Unix time in milliseconds;
- `commandNonce`: 16 random bytes, base64url.

The signed message is the UTF-8 JSON of:

```json
{"v":1,"action":"enqueue","queueId":"q_...","token":"...",
 "signedAt":1700000000000,"commandNonce":"...","packet":"...",
 "pow":{"nonce":123,"digest":"..."}}
```

Field order is fixed. `token` is the relevant bearer token. Action-specific
fields are `packet` for `enqueue`, `limit` for `poll`, `packetIds` for `ack`,
and none for `delete_queue`. `pow` is included for `enqueue` only when the
invite carries a challenge and the queue has not consumed it. `signedAt` must be
within 5 minutes of relay time and no more than 60 seconds in the future. A
reused `commandNonce` is rejected.

### enqueue

`POST /api/anon/enqueue` with `queueId`, `senderToken`, fixed-size `packet`,
and signed-command fields when the queue has a signing key.

Rules:

- validate sender token against its stored hash;
- verify the queue-key signature, timestamp, and command nonce;
- if the queue has an unused `pow` challenge, require a valid solution and mark
  it used; missing solution returns `POW_REQUIRED`, bad solution
  `INVALID_POW`;
- reject if queue is expired or missing;
- require the decoded packet length to be exactly 4096, 16384, or 65536 bytes;
- store ciphertext only;
- apply per-IP rate limits (100/min in the reference server);
- reject when the queue has 200 packets;
- return `packetId` and `expiresAt`.

### poll

`POST /api/anon/poll` with `queueId`, `recipientToken`, `limit`, and
signed-command fields when the queue has a signing key.

Rules:

- validate recipient token against its stored hash;
- verify the queue-key signature, timestamp, and command nonce;
- return packets not yet acked and not expired;
- clamp `limit` to 1-100 (default 32);
- do not delete on poll;
- apply jitter on client side (not wired in v1).

### ack

`POST /api/anon/ack` with `queueId`, `recipientToken`, `packetIds`, and
signed-command fields when the queue has a signing key.

Rules:

- validate recipient token;
- verify the queue-key signature, timestamp, and command nonce;
- delete acked packets immediately;
- expired packets are deleted by cleanup;
- no rate limit is applied to ACK in the reference server.

### delete_queue

`POST /api/anon/queues/delete` with `queueId`, `recipientToken`, and
signed-command fields when the queue has a signing key.

Validates the recipient token and signed command, then deletes the queue and
all packets. No rate limit is applied in the reference server.

### route (relay side of a proxy hop)

`POST /api/anon/route` accepts `{ envelope }` and dispatches `enqueue`, `poll`,
`ack`, `create`, or `report`. The envelope is X25519 + HKDF-SHA256 + AES-256-GCM
sealed to the relay's routing key. An `enqueue` plaintext looks like:

```json
{"v":1,"iat":1700000000000,"nonce":"...","action":"enqueue",
 "queueId":"q_...","token":"...","packet":"...",
 "signature":"...","signedAt":1700000000000,"commandNonce":"...",
 "pow":{"nonce":123,"digest":"..."}}
```

A `create` plaintext carries `ttlMs`, `replyPublicKey`,
`signingPublicKey`, and optional `pow` instead of queue credentials. The relay creates the queue and
returns `{ok:true,envelope}`, where `envelope` is sealed to `replyPublicKey` and
contains `{action:"create",queueId,senderToken,recipientToken,expiresAt}`. The
proxy cannot read either side.

A `report` plaintext contains only a random id, the SHA-256 hashes of the
reported queue id and signing key, and a coarse category (`spam`,
`harassment`, or `illegal`). It contains no invite, tokens, free text, or
client-supplied timestamp. The relay accepts retries idempotently, limits
reports per proxy client key, caps the in-memory report store, and expires
reports after 90 days. The report id and report contents are encrypted from the
proxy; the relay sees the proxy's address and the hashed target. Reports are
persisted as one hash-only JSON file per report id (`ANON_REPORTS_DIR`,
default `./anon-reports`), reloaded at boot and deleted when they expire, and
they are no longer inert: queue creation is limited to 10
queues per hour per signing key (bucketed on the key hash, independent of the
per-client limit), and a signing key with at least 3 live `spam`-reported queues
is refused creation with `SIGNING_KEY_BLOCKED` until those reports expire.
`harassment` and `illegal` reports are stored but do not affect creation.
A report only counts when its queue hash names a queue the relay itself issued
for that signing key; anything else gets `UNVERIFIED_REPORT`. The threshold
counts distinct queues, not report ids, so padding one queue with many ids does
nothing. Queue ownership is remembered for 7 days past the queue's expiry, and
since the queue table lives in RAM a report about a queue from before the last
restart is rejected.
Enqueueing on existing queues is not restricted by reports: a blocked key keeps
the contacts it already made.

The relay opens the envelope with `ANON_ROUTING_PRIVATE_KEY`, rejects envelopes
older than 5 minutes or more than 60 seconds in the future, and rejects a
replayed `nonce`. Queue commands inside the envelope use the same queue-key
signature, timestamp, and command-nonce checks as the direct endpoints. The
route endpoint is rate limited per client key; queue operations are also limited
per queue, create is limited per client key, and report submissions have an
additional per-client rate limit.

`GET /api/anon/routing-key` returns the relay's public routing key. Clients must
pin it; fetching it through the same untrusted channel on every request defeats
the guarantee. Generate a persistent key with:

```sh
node -e "import('./src/lib/anon/routing.js').then(m => console.log(m.generateRoutingKeyPair().privateKey))"
```

### hop (proxy side)

`POST /api/anon/hop` accepts `{ relay, envelope }`, resolves `relay` through the
server-side `ANON_PROXY_TARGETS` allowlist, and forwards only `{ envelope }` to
`<target>/api/anon/route`.

The proxy sees the destination relay id, ciphertext, request timing, and size; it
must not see queue ids, bearer tokens, or packet contents. Sealed queue creation
is available through this path; the direct `/api/anon/queues` endpoint remains
legacy.

## 5. Storage rules

- Queues are held in `anonQueues` (`server.js`) and persisted to a local
  SQLite file at `ANON_STATE_DB_PATH` (default `./anon-state.sqlite`). A process
  restart reloads non-expired queues and packets; a container needs a
  persistent volume for that path. If SQLite is unavailable or the path is
  empty, the relay falls back to memory-only operation.
- Per queue it stores `queueId`, `senderTokenHash`, `recipientTokenHash`,
  `signingPublicKey`, optional `pow` challenge, `powUsed`, `createdAt`,
  `expiresAt`, and packets (`packetId`, base64 payload, `createdAt`,
  `expiresAt`). Each queue is one inbox; the relay does not store a
  sender/recipient queue pair.
- The `queueIdHash -> signing key hash` owner index is persisted next to the
  queues, so reports about existing queues still work after a restart. Rate
  limit buckets and replay nonces remain in memory.
- Queue TTL: 14 days default, 21 days maximum. Packet TTL: 24 hours.
- Per-queue cap: 200 packets.
- Routing nonces are cached in memory for 5 minutes to reject envelope replay.
  Command nonces are also cached for 5 minutes to reject duplicate signed
  commands.
- Delete on ACK; expired queues and packets are removed by a 60-second cleanup.
- No request-body or IP logging is implemented for the anon endpoints; keep it
  that way.

## 6. Security rules

- All packets are fixed-size.
- Padding bytes are random.
- Sender and recipient tokens are generated with 32 bytes of CSPRNG output.
- Queue signing keys are Ed25519; private keys stay in invites, public keys at
  the relay.
- First-contact PoW is SHA-256 with 1-24 leading zero bits over
  `challenge || nonce`; the relay verifies it before accepting queued data.
- Queue IDs are 16 bytes of CSPRNG output.
- Relay must not log request bodies.
- Client should use TLS to relay (and proxy/Tor in later phases). Invite decoding
  rejects non-HTTPS relay URLs except loopback and `http://` `.onion` hosts
  (which are authenticated/encrypted by the onion circuit); direct transport
  config should enforce the same.
- The proxy sees the destination relay id and request timing, but not queue ids,
  tokens, or packet contents. Pairing uses independent queue IDs; the relay can
  still correlate timing, and direct transports leak IPs. Use proxy/Tor for IP
  separation. The raw legacy API does not enforce pairing.
- Queue-key signatures authenticate possession of the queue signing key and bind
  commands to the queue, token, timestamp, and action. They do not authenticate
  a human identity: anyone who receives an invite also receives its signing key
  and can inject messages. Sealed sender gives confidentiality but not sender
  authentication.
- Push (phase F): `POST /api/anon/push/register` stores only
  `pushToken -> queueId`; `GET /api/anon/push/hint` returns the bound queue id
  and an empty hint. The client derives one opaque token per queue, so the
  notification service never learns that two queues belong to one device. When
  `ANON_PUSH_WEBHOOK_URL` is set, the relay POSTs `{ "token": "..." }` (no queue
  id, sender, or content) to the bridge. The app polls on a hint and verifies
  everything as usual; push registration is disabled while a proxy is
  configured.

## 8. Residual risks and current blockers

Current blockers before this protocol can be called anonymous v1:

- The experimental `AnonymousMessengerScreen` uses sealed create plus
  `pairing.ts`, but the direct create endpoint and legacy single-queue usage
  still exist outside that isolated screen.
- Clients must pin the relay routing public key; key distribution is not automated.
- One-time invites must be enforced server-side; queue-key signatures and
  first-contact PoW are enforced for new queues.
- Invite decoding enforces expiry and HTTPS/localhost; direct transport config
  must apply the same policy when the app is wired.
- The isolated screen stores contacts and messages in the encrypted local
  database and saves valid incoming packets before ACK. Ordinary chat history,
  attachments, retries, and background polling are not integrated.

Residual risks:

- Global passive observer can correlate timing.
- Compromise of both proxy and relay removes two-hop protection.
- The proxy sees the destination relay id, request timing, and envelope sizes.
- Independent inbox queues are unlinkable by ID, but timing and IP correlation
  remain; direct mode leaks both parties' IPs.
- `/api/anon/route` is publicly reachable; deployments should restrict it to
  proxy IPs or a private network.
- Relay responses are not end-to-end authenticated; a malicious proxy can drop
  or fabricate responses. It cannot forge E2EE message contents.
- The routing nonce cache is in-memory; a restart forgets recent nonces.
- Push providers see notification events.
- Device compromise bypasses all protections.
- Sealed sender does not authenticate the sender.
