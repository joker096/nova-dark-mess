# Подробный план интеграции функций безопасности и P2P (Mess&Anger -> Nova Dark Messenger)

Данный документ содержит исчерпывающее техническое руководство по переносу архитектуры безопасности, сквозного шифрования (E2EE), децентрализации и резервного копирования из репозитория [joker096/neumorphic-ui](https://github.com/joker096/neumorphic-ui) (Mess&Anger) в текущий проект **Nova Dark Messenger** (`nova-dark-messenger`).

> **Главный принцип интеграции:** Visual UI & UX приложения Nova Dark Messenger остаются абсолютно неизменными. Все компоненты интерфейса (`ChatScreen`, `ProfileScreen`, `SettingsModal`, стили Tailwind и анимации Framer Motion) сохраняют свой текущий вид. Изменения затрагивают исключительно архитектурный слой данных, криптографические сервисы, P2P-транспорт и локальное хранилище.

---

## 1. Архитектурный обзор и сравнение систем

| Функция | Текущая реализация (Nova Dark) | Новая архитектура (Mess&Anger Backend Engine) |
| :--- | :--- | :--- |
| **Идентификация** | Моковые данные / профили пользователей | Анонимная криптографическая пара ключей (Ed25519 / X25519). Без номеров телефонов и email. |
| **Аутентификация** | Локальная / сессионная | Мнемоническая seed-фраза (BIP-39, 12/24 слов) + локальный PIN-код. |
| **Шифрование сообщений** | Отсутствует (открытый текст в памяти) | End-to-End Encryption (E2EE) с использованием протокола **Double Ratchet** и **X3DH**. |
| **Транспорт сообщений** | Обычные HTTP/WS моки | **Serverless P2P** через WebRTC DataChannels + децентрализованная ретрансляция (Mesh / Multi-hop Relay). |
| **Хранилище данных** | In-memory React State / LocalStorage | Зашифрованная локальная СУБД (IndexedDB + AES-256-GCM, ключ деривирован через Argon2id / PBKDF2). |
| **Резервное копирование** | Нет | Зашифрованные экспорт/импорт файла бэкапа (`.nova-backup`) без участия сторонних серверов. |
| **Безопасность узла (2FA)** | Отсутствует | RFC 6238 TOTP 2FA + Proof-of-Work (PoW) для защиты от спама на сигнальном сервере. |

## 2. Модуль 1: Анонимность и бестелефонная идентификация

### 2.1 Концепция
Отказ от номеров телефонов, логинов и паролей на сервере. Идентификатором пользователя в сети является хэш его публичного ключа (Fingerprint / ID, например: `nova_pk_8f3a...91c2`).

### 2.2 Криптографические стек
* **Ed25519**: Используется для цифровой подписи сообщений и подтверждения подлинности.
* **X25519**: Используется для обмена ключами по схеме Диффи-Хеллмана (Diffie-Hellman Key Exchange).
* **BIP-39**: Генерация мнемонической фразы (12 или 24 слова) из 256-битного энтропийного источника (Web Crypto API `crypto.getRandomValues`).

### 2.3 Логика внедрения
1. Создать крипто-сервис `src/lib/crypto/identity.ts`:
   ```typescript
   export interface UserIdentity {
     publicKey: string;       // Hex / Base64 X25519 public key
     signingKey: string;      // Hex Ed25519 public key
     fingerprint: string;     // SHA-256 (signingKey)
     mnemonic?: string;       // BIP-39 seed phrase (хранится только во время показа пользователю)
   }
   ```
2. При первом запуске Nova Dark Messenger, если ключи отсутствуют в локальном хранилище, автоматически генерируется новая Identity.
3. В `ProfileScreen.tsx` при клике на "Скопировать ID" копируется `fingerprint` / `publicKey` вместо мокового ID.
4. В `SettingsModal.tsx` добавляется пункт "Показать резервную фразу (Seed Phrase)" с подтверждением локального PIN-кода.

## 3. Модуль 2: Сквозное шифрование (E2EE) и Double Ratchet

### 3.1 Архитектурный протокол (Signal Protocol / Double Ratchet)
Протокол Double Ratchet обеспечивает два критически важных свойства безопасности:
1. **Perfect Forward Secrecy (PFS)**: Компрометация текущего сеансового ключа не позволяет расшифровать ранее отправленные сообщения.
2. **Post-Compromise Security (PCS)**: Если ключ был скомпрометирован, сеть автоматически восстанавливает защиту при следующем ответе собеседника.

```
[Пользователь А]                                               [Пользователь Б]
  (X25519 / Ed25519)                                            (X25519 / Ed25519)
         |                                                               |
         |-------------- 1. X3DH Handshake (PreKey Bundle) ------------>|
         |                                                               |
         |<============= 2. P2P WebRTC / Encrypted Relay ===============>|
         |                                                               |
    [DH Ratchet Step]                                           [DH Ratchet Step]
    [Symmetric Ratchet] -- Message Encrypted (AES-256-GCM) ----> [Symmetric Ratchet]
```

### 3.2 Техническая реализация шифрования
1. **Инициализация сессии (X3DH)**:
   * Каждая сторона публикует набор одноразовых ключей (One-Time Prekeys) и подписывает их своим Identity Key.
   * Отправитель берет Prekey получателя, вычисляет общий секрет `Master Key` и инициализирует Ratchet.
2. **Симметричное и DH-обновление (Ratchet Steps)**:
   * Для каждого нового сообщения генерируется уникальный `Message Key` (HMAC-SHA256 KDF).
   * После получения ответа собеседника обновляется асимметричная пара X25519 (DH Ratchet step).
3. **Структура пакета зашифрованного сообщения**:
   ```typescript
   export interface EncryptedPayload {
     version: number;            // Версия протокола (напр. 1)
     ephemeralPublicKey: string; // Временный ключ X25519
     sequenceNumber: number;     // Номер сообщения в цепочке (Ratchet counter)
     previousChainLength: number;// Длина предыдущей цепочки
     ciphertext: string;         // Base64 AES-256-GCM payload
     nonce: string;              // 12-byte IV/Nonce
     authTag: string;            // GCM Auth Tag
   }
   ```

## 4. Модуль 3: P2P Мессенджинг и бессерверная сеть (Serverless / Mesh)

### 4.1 Архитектура соединений
Приложение поддерживает гибридную схему доставки сообщений:
1. **Прямой P2P WebRTC DataChannel** (Основной транспорт):
   * Сообщения передаются напрямую между браузерами пользователей без сохранения на промежуточных серверах.
   * Задержка минимизирована (Real-time Latency < 50ms).
2. **Сигнальный сервер (Signaling Server)**:
   * Используется **только** для обмена SDP-офферами/ответами и ICE-кандидатами при установлении WebRTC-соединения.
   * Сервер не имеет доступа к содержимому сообщений и не сохраняет историю переписок.
3. **Multi-hop Relay (Ретрансляция при невозможности P2P)**:
   * Если оба клиента находятся за строгими NAT/Firewall (Symmetric NAT), включение луковой (Onion-style) ретрансляции через промежуточные пиры с зашифрованными конвертами.

### 4.2 Схема интеграции в Nova Dark Messenger
* Создать менеджер WebRTC в `src/lib/p2p/p2pManager.ts`:
  * `connectToPeer(peerPublicKey: string)`
  * `sendMessage(peerPublicKey: string, payload: EncryptedPayload)`
  * `onMessageReceived(callback: (senderPk: string, payload: EncryptedPayload) => void)`
* В `src/components/ChatScreen.tsx` заменить прямой вызов добавления мокового сообщения на отправку через `p2pManager`.

## 5. Модуль 4: Локальное шифрованное хранилище и бэкапы

### 5.1 Безопасность локальных данных (Encrypted Local Storage)
Все данные (история чатов, контакты, медиафайлы, неактивные ключи) должны храниться в **IndexedDB**, зашифрованные на лету.

1. **Деривация ключа хранилища (Key Derivation)**:
   * Входные данные: PIN-код или пароль пользователя + уникальная соль (Salt).
   * Алгоритм: **Argon2id** (или PBKDF2 с 600,000 итерациями в качестве браузерного fallback).
   * Результат: 256-битный Master Storage Key (MSK).

2. **Шифрование данных**:
   * Для любой записи в IndexedDB используется **AES-256-GCM**.
   * В открытом виде хранится только служебная мета-информация БД (идентификаторы таблицы), весь контент зашифрован.

### 5.2 Логика Резервного Копирования и Восстановления (Backup & Restore)
* **Экспорт (`.nova-backup`)**:
  1. Из IndexedDB извлекаются все зашифрованные таблицы.
  2. Данные упаковываются в единый JSON/Binary файл.
  3. Файл шифруется еще раз с использованием ключа, полученного из мнемонической фразу (Seed Phrase) или специального пароля бэкапа.
  4. Скачивание файла происходит через встроенную в браузер генерацию blob.
* **Импорт (Восстановление)**:
  1. Пользователь загружает файл `.nova-backup`.
  2. Вводит мнемоническую фразу или пароль бэкапа.
  3. Приложение расшифровывает заголовок, валидирует целостность (HMAC/GCM Tag) и восстанавливает структуру IndexedDB.

## 6. Модуль 5: 2FA и безопасность сигнальной инфраструктуры

### 6.1 Двухфакторная верификация (2FA / TOTP)
Для защиты от несанкционированного доступа к сигнальным серверам или панели управления инстансом (например, при развертывании своего сигнального узла):
* **Алгоритм**: RFC 6238 TOTP (SHA-1 / SHA-256, 6 цифр, шаг 30 секунд).
* Совместимость с Google Authenticator, Microsoft Authenticator, Aegis, Bitwarden.

### 6.2 Защита сигнального узла от DDoS и спама
1. **Proof-of-Work (PoW) Challenge**:
   * Перед установлением WebSocket-соединения с сигнальным сервером клиент должен решить легкую вычислительную задачу (например, найти nonce для SHA-256 с заданной сложностью). Это защищает сервер от ботнетов.
2. **Rate Limiting & Token Bucket**:
   * Ограничение количества сигнальных запросов на один IP/Public Key (не более 10 запросов в секунду).

## 9. Проверка и верификация решения

1. **Проверка сохранения UI**: Все пользовательские интерфейсы работают без визуальных изменений.
2. **Типобезопасность**: Запуск `npm run lint` (`npx tsc --noEmit`) должен проходить без ошибок.
3. **Криптографические тесты**: Проверка корректности работы Double Ratchet (отсутствие дешифрования при нарушении последовательности nonces или компрометации ключей).
